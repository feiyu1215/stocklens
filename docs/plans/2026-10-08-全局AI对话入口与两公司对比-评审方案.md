- 日期：2026-10-08

## 一、背景

### 1.1 产品是什么

StockLens 是一个 A 股单公司研究工具，核心产品是「研究空间」：用户选定一家公司后，系统生成七个研究维度（增长韧性、盈利质量等），每个维度挂真实证据（财报事实、行情数据），基于证据生成研究结论（claims），全程贯彻 Evidence first——每句话都能溯源到具体证据。目前有三个用户面：

1. **首页（/）**：搜索框 + 公司选择 + 研究问题输入，是进入研究空间的入口；
2. **研究库（/research 的 library surface）**：已研究公司的矩阵/列表，数据存在本机（IndexedDB）；
3. **研究空间画布（/observatory-v5）**：核心工作区，内有 AI 对话面板（Sidekick），可以围绕当前公司的证据追问。

### 1.2 三个问题的来源

用户（产品作者）提出，AI 对话目前只在研究空间里有，其他地方（首页、研究库矩阵）的搜索只是入口。设想：

> "如果你把那个对话窗口作为一个全局的展开，那这里就可能就会方便一点，它可以承接一些正常的非选择公司的对话。比如说在矩阵里面，你可能会问'你觉得以下哪几家公司需要进行关注'，那它就会参考所有的公司。也可以直接在首页直接去问……甚至更进一步，类似 iPhone 的 AssistiveTouch 悬浮球——用户选择开启它，就可以通过这个 AI 对话入口控制产品，做一些基本的跳转。"

由此引出三个问题：

- **Q1**：把 Sidekick 做成全局可展开的悬浮球（AssistiveTouch 式），承接非公司对话 + 作为产品导航/命令入口——方便实现吗？
- **Q2**：如果在首页对话并想"进入研究"，承载形态是什么？是创建一个"非公司个体的研究区域"，还是只是页面上的 AI 对话小窗口？
- **Q3**：此前提过的"两公司对比"功能，交互方式应该怎样设计？（并联系全局对话入口）

### 1.3 前情教训：首页 chip 假状态事件（同一条纪律）

2026-10-08 晚，首页三个快捷问题 chip 被用户报告"点了没反应"。第一轮修复把问题输入区提前展开（未选公司也能填问题），随即被用户否定：

> "如果说他先写的问题，咱没选公司，那其实是不符合我们的这个场景的，因为我们没有提供一个通用的分析能力，不是吗？"

最终修正：问题依附公司存在；chip 只做"预选角度 + 聚焦搜索框 + 提示先选公司"。**这条纪律适用于本次全部三个问题：产品没有的能力，任何入口都不许让用户以为有。**全局 AI 入口如果假装能答"哪几家公司值得关注"，就是把 chip 的假状态升级成常驻悬浮球版本。

### 1.4 能力现状

后端 AI 目前只有一种分析模式：**单公司、基于该公司证据的追问**（followup）。没有市场级/多公司分析能力；没有通用对话通路。数据层（Truth Layer）按 stockCode 逐家加载，每次调用重跑，无服务端持久化。

## 二、代码现状核验（评审者可复核的硬事实）

以下事实均在 2026-10-08 于工作区实际核验，附验证位置。

**F1：followup API 单公司硬绑定。**
`src/app/api/followup/route.ts:15` 用正则 `^\d{6}\.(SZ|SH|BJ)$` 强制请求体恰好一个 A 股代码；`src/lib/ai/followup.ts:55` 每次调用重跑 `loadTruthForResearch(stockCode)`（Truth Layer 无持久化，秒级开销）；`followup.ts:91` 焦点证据为空直接判失败——**不存在"无公司上下文的对话"通路**。

**F2：Sidekick 面板与研究 payload 深度耦合。**
`src/components/v5/ResearchSidekickPanel.tsx`（485 行）props 直接吃 `ResearchSpacePayload`，SOURCES 列表要按证据 ID 链接到画布证据卡，上下文项类型是 company/dimension/claim/evidence 四种。直接复用做全局面板不可行，但抽取一个"无公司上下文的轻量聊天壳"可行（工作量见方案 A）。

**F3：证据 ID 无公司前缀。**
`src/lib/evidence/fact-builder.ts:338` 生成 `EV_FACT_${metricId}`，不含公司代码。两家公司的证据合并必然 ID 冲突（这正是此前评估 P2-1 多公司并列时已记录的问题）。**任何多公司功能（对比、矩阵级问答）都绕不开先修 ID 命名空间。**

**F4：研究库本地存全量 payload。**
每家公司 payload 约 70,908 字节（含证据、指标、claims、日线），存 IndexedDB（`src/lib/v5/idb.ts` + `shelf.ts`，带配额自愈）。含义：**库里已研究过的公司做对比，客户端就有全部数据，不需要动后端。**

**F5：合规守卫现成可复用。**
`src/lib/validation/compliance.ts` 的 `detectRestrictedInvestmentRequest` 已在 followup / diagnosis 两个入口接入，投资建议类问题在进 LLM 前拦截并返回引导话术。全局对话入口必须同样接上。

**F6：Evidence 自带七值维度枚举。**
`Evidence.dimension` 是固定枚举（growth / profitability 等），与研究空间的动态维度 ID（`DIM_AI_INITIAL_01_增长韧性`）不同。含义：**两公司对比的"逐维度对齐"可以用这个稳定枚举做 join key，不依赖两边动态维度是否同名。**

## 三、三个问题与提出方的立场

### Q1 全局悬浮球入口 → 立场：做，但按"调度层"做，不按"能力层"做

设计依据是对话式界面的一条长期结论：**对话是调度层，不是能力层**。Alexa 类助手的信任崩塌源于入口做出"什么都能问"的通用感而后端能力有限；做得对的混合入口（命令面板 + AI）都是先把用户的话分类成"能真实兑现的几种意图"。

具体设计——悬浮球展开后，用户每句话被意图路由分成四类：

1. **导航类**（"打开美的的研究""看看我的研究库""导出这份笔记"）→ 执行跳转/动作。这是 AssistiveTouch 语义，用小模型调用 + 固定动作表即可实现，不需要任何市场数据，便宜且低风险。
2. **产品/概念问答类**（"市盈率在哪看""这个证据的口径是什么意思"）→ 直接回答。这类不需要市场数据，是**真实的通用能力**，不违反能力诚实。
3. **单公司分析类**（"美的最近怎么样"）→ 需要公司上下文。若当前不在研究空间，引导选择公司后走现有 init 流程；若在画布内，走现有 Sidekick 链路。
4. **多公司分析类**（"你觉得哪几家值得关注""对比美的和格力"）→ 当前无能力兑现。诚实做法：明说"多公司分析我们用对比页来做"，移交到对比表面（见 Q3）；矩阵级"哪几家值得关注"暂无承载，如实告知分析从一家公司开始。

### Q2 承载形态 → 立场：不做"非公司研究区域"，对话就是全局浮层

理由：研究空间的整个 schema（维度、证据锚点、claims、Evidence first 校验、持久化、笔记导出、证据快刷）全部绑死单公司，拆绑定等于重做半个产品；且产品语义上研究空间是**结构化的证据资产**（可导出、可快刷、可重组织），一段对话不构成这种资产。对话是情景性的——聊完留下的应该是"去研究了美的"这个动作，不是一个新的研究区域。所以 Q2 的答案是用户设想的第二种：**全局对话 = 悬浮球展开的对话面板**，聊到要深入某家公司就触发现有 init 流程跳进研究空间，不新建任何区域类型。

### Q3 两公司对比 → 立场：做专用表面，不做聊天气泡；入口在研究库多选 + 对话意图触发

对比的本质是"逐维度并排 + 证据可溯源"，聊天气泡承载不了证据锚点，硬塞违反 Evidence first 的展示纪律。交互设计：

- **入口一（主要）**：研究库多选两家公司 → 出现"对比"按钮；
- **入口二**：全局对话识别对比意图（"帮我对比美的和格力"）→ 打开对比页并预载两家（与 Q1 第 4 类意图衔接）；
- **页面形态**：左右两列按 Evidence 七值维度枚举（F6）对齐，每格证据可点开溯源；顶部一段 AI 综合摘要（新 compare 接口，双 stockCode、双份证据各加公司命名空间）；
- **分期**：先做库里存量公司的客户端对比（数据现成，F4），再上服务端实时对比 + 摘要。

## 四、最强反方与前提标注

**反方 A（最强）：没有通用分析能力的悬浮球就是个高级导航栏，用户很快会觉得它笨，这个功能值不了一期。**
回应：产品问答（第 2 类）是真通用能力，加上诚实的分析引导和对比移交，第一期已比"点不动的 chip"强一个量级；且调度层的意图识别和聊天壳是地基——市场级分析能力立项时入口直接复用。但要承认：如果用户高频问题集中在第 4 类，第一期的体验确实是"球很聪明但答不了你最想问的"。这是本方案最大的产品风险，请评审者重点评估。

**反方 B：对比先凑合用聊天文本输出，不用做专用页面。**
回应：不接受。证据溯源在气泡里无法点击，违反产品最核心的 Evidence first 展示纪律；且多公司证据合并撞 ID（F3）是硬约束，绕不开前置修复，"凑合"并不省事。

**反方 C：现状已自洽（Sidekick 在画布内、chip 语义刚修好），此时加全局入口是机会成本。**
回应：部分成立。现状确实自洽，方案 B（见下）不是坏选择。支持做 A 的增量理由：用户已在真实使用中提出矩阵级/跨公司提问诉求（本次三个问题的来源本身就是需求证据），缺口是真实存在的，只是当前用"沉默"处理。

**前提标注与判断动作：**

| 前提 | 来源 | 判断动作 |
|---|---|---|
| followup 单公司硬绑定、无通用通路 | 事实（代码核验，F1） | 直接成立 |
| 聊天壳可从 Sidekick 低成本抽取 | 推测（仅静态阅读，未动手） | 成本按上限报（2–3 天含抽取）；若抽取中发现耦合过深，降级为新写轻量面板 |
| 意图路由小模型调用便宜可靠 | 迁移（业界通例 + 项目内 planner 经验） | 第一期验收必测路由准确率；不达标则砍掉意图分类、降级为纯导航入口 |
| 用户对矩阵级提问的诉求是真实高频需求 | 推测（来自用户单次提出） | 评审者判断项之一 |

## 五、方案 A：做（分期执行计划）

### 阶段 1：全局对话入口（悬浮球），预估 2–3 天

1. **聊天壳抽取**：从 `ResearchSidekickPanel` 抽出无公司上下文的消息流壳（消息列表、输入框、状态态、流式/加载态），公司相关部分（SOURCES 溯源、维度上下文）留在画布原面板。产物：`src/components/v5/GlobalChatPanel.tsx`（或共享壳 + 两个包装）。
2. **悬浮球组件**：右下角浮动按钮，展开为对话面板；localStorage 记忆开关（用户可选择关闭，尊重 AssistiveTouch"用户选择开启"的语义）；移动端默认关闭。client-only，不阻塞任何页面首屏。
3. **意图路由**：新 API（如 `/api/chat/dispatch`），小 max_tokens 的单次 LLM 调用，输出固定 schema（intent: navigate / product_qa / company_analysis / out_of_scope，附 action 参数或答案文本）。导航动作表白名单（打开某公司研究、研究库、导出笔记等现有功能），**动作必须白名单校验，防 LLM 幻觉出不存在的操作**。纯导航意图不接任何证据链路。
4. **三面接入**：首页、研究库、画布挂同一个悬浮球；画布内可感知当前公司上下文（第 3 类意图直接接现有 followup）。
5. **纪律落实**：合规守卫（F5）接入；第 4 类意图固定话术移交对比页或明说无能力；**测试断言"分析类问题绝不出现编造的回答"**。
6. **验收信号**：三类意图各实测一条完整链路（导航跳转到位 / 产品问答有真实答案 / 引导选公司闭环）；合规拦截生效；悬浮球可关；现有 454 项测试不破。

**成功信号**：意图路由准确率实测达标；用户测试中无人把悬浮球当成"全能分析师"后被辜负。
**失败/转向条件**：路由准确率低 → 砍意图分类降级为纯导航 + 固定快捷动作；抽取成本超预估 2 倍 → 回退方案 B 并归档决策。

### 阶段 2：两公司对比，预估 3–4 天（依赖阶段 1 的移交话术，但不依赖其代码）

1. **ID 命名空间修复**（前置，必须）：多公司合并场景下证据 ID 加公司前缀映射（合并时改写，不动物理生成——避免破坏存量 payload 与既有测试）。含差分校验口径确认。
2. **客户端对比页（Phase 2a）**：研究库多选两家 → 对比页；数据取自两家存量 payload（F4），按 Evidence 七值枚举（F6）逐维度并排，证据可点溯源；无 AI 摘要（纯结构化对比先上）。路由如 `/research/compare?stocks=A,B`。
3. **服务端实时对比 + AI 摘要（Phase 2b）**：新 compare 路由（双 stockCode，分别跑 Truth Layer，证据各自命名空间后合并喂给一次 LLM 摘要调用，复用合规守卫）；摘要挂在对比页顶部，逐条可溯源。
4. **验收信号**：双公司证据零 ID 冲突；每格证据可溯源；只存在于库中的公司可对比（2a）/任意公司可对比（2b）；摘要素材 100% 引用真实证据。

### 方案 A 不做什么（边界）

- 不做非公司研究区域（Q2 已否决，理由见前）；
- 不做矩阵级"哪几家值得关注"的真实分析（无能力，等市场级分析单独立项）;
- 不做三家及以上对比（交互复杂度另议）；
- 不改现有 Sidekick 在画布内的任何行为。

## 六、方案 B：不做（同样不是"什么都不做"）

1. **维持现状**：AI 对话保持在画布内；首页/研究库不挂悬浮球；
2. **归档决策**：把本次三个问题与结论写进 backlog（矩阵级问答、两公司对比、全局入口），注明触发条件（如"出现市场级数据能力后重议矩阵问答"）；
3. **如实声明用户缺口**：用户在首页/矩阵想问分析问题时产品无承载——接受这个沉默，因为编造承载更糟（chip 教训）；
4. **最小补丁（可选，半天）**：仅在研究库给两条以上存量公司加一个无 AI 的纯客户端对比视图（方案 A 阶段 2a 的子集），作为缺口的最低成本兜底。

方案 B 的适用条件：评审认为悬浮球价值不足（反方 A 成立）、或排期与交付冲突、或用户测试显示第 4 类意图占比远高于其他类（此时第一期体验反而伤害产品信任）。

## 七、请评审者明确回答的问题

1. **总立场**：方案 A（分期做全局入口 + 对比）还是方案 B（不做 + 归档 + 可选最小补丁）？或给出第三条路。
2. **意图四分类**（导航 / 产品问答 / 单公司引导 / 多公司移交）的边界是否认可？尤其"产品问答"类是否属于应该做的真实能力，还是也该砍掉以进一步收缩承诺？
3. **Q2 否决"非公司研究区域"** 是否成立？有没有被忽略的第三种承载形态？
4. **对比分期**（先客户端存量、后服务端实时）顺序是否认可？ID 命名空间"合并时改写、不动物理生成"的折衷是否有隐患？
5. **反方 A 的评估**：第一期"答不了用户最想问的"这一风险，是否足以推翻整个一期？

## 八、本方案不解决什么

- 市场级/大盘数据分析能力（未立项，无数据层支撑）；
- followup 每次重跑 Truth Layer 的性能问题（现状秒级，未成瓶颈，不动）;
- git 推送远端、国内 CloudBase 包上传（既有待办，与本题无关）；
- 移动端悬浮球的完整交互（一期只保证"默认关闭 + 可开"，深度移动端适配待真机反馈）。
