## 三、五个失败用例与根因

混淆矩阵：

| 期望 → 实际 | 条数 |
| --- | --- |
| product_help → company_research | 3 |
| compare → company_research | 1 |
| company_research → navigate | 1 |

### 根因 1：`COMPANY_RESEARCH` 正则把「研究」后面的字当成公司名（3 条）

`src/lib/v5/assistant/rules.ts:29`

```ts
const COMPANY_RESEARCH = /(?:研究|分析|看看)\s*([\u4e00-\u9fa5A-Za-z0-9]{2,10})(?:最近|的)?(?:怎么样|如何|表现)?/
```

该规则在**产品功能清单之前**执行，因此任何含「研究」二字的问题都会被它截走：

| 用例 | 被抓出的"公司名" | 系统回答 |
| --- | --- | --- |
| 研究库怎么用 | 「库怎么用」 | 没有在 A 股（沪深北）中找到「库怎么用」 |
| 如何导出研究笔记 | 「笔记」 | 没有在 A 股（沪深北）中找到「笔记」 |
| 开始之前填的那个研究问题有什么用 | 「问题有什么用」 | 没有在 A 股（沪深北）中找到「问题有什么用」 |

三条都本应先走 `findProductFeature`（公司搜索 / 导出笔记 / 研究问题均在功能清单内）。**修复方向**：把产品功能清单的确定性匹配提到 `COMPANY_RESEARCH` 之前；或在该规则的捕获后加白名单排除（库 / 笔记 / 问题 / 摘要 / 面板），并要求公司名后接边界（助词、标点或句尾）。

### 根因 2：同类正则抢在 compare 之前吃掉第一个提要词（1 条）

`看看 NVIDIA 和 AMD` → `看看` 先匹配到 `NVIDIA` → company_research。
**修复方向**：在执行 `COMPANY_RESEARCH` 前，先检测"两个候选名 + 分隔符（和/与/跟/vs/空格）"的对比句式。

### 根因 3：`打开 <公司名>` 缺后缀时规则不命中，落到 LLM 被判成导航（1 条）

`打开海康威视` → `COMPANY_OPEN`（`rules.ts:28`）要求「的研究 / 画布 / 空间」后缀，裸公司名不命中 → LLM 把"打开"理解成开页面 → 返回两张导航卡片。
**修复方向**：补一条 `(?:打开|进入|切换)\s*([\u4e00-\u9fa5]{2,6})\s*$`，命中后走既有的 `resolveCompanyAction`（实体解析仍然是真实检索，不猜代码）。

## 四、这份数据说明了什么

1. **分层设计有效**：规则层 + 产品清单 + LLM 兜底的组合下，10  unsupported（含 5 条投资建议）全部被确定性防线接住，没有一条漏给模型去"自觉"判断——这是产品最需要硬的地方，是硬的。
2. **贪心的规则比不可靠的模型更危险**：5 个错判里 4 个来自规则层过度捕获，0 个来自 LLM 幻觉。规则一旦写宽，就会把用户和问题都带偏，而它看起来还"很确定"（系统自信地回答"没有找到「库怎么用」"）。
3. **改这三处的收益**：按上述方向修完再跑同一标注集，期望提升到 **96.7%（58/60）**——剩余那条 `打开海康威视` 取决于是否愿意让 `打开 + 公司名` 直接触发（涉及是否要牺牲"打开首页"类短语的安全性，属产品取舍）。
