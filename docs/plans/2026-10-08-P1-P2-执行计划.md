## 1. 为什么是这个顺序

不是按原清单的 P1→P2，也不是按"先易后难"。排序标准是：**先做不依赖产品决策、且能立刻被看见的三项，把唯一有原则风险的一项放到最后。**

| 序 | 是否需要产品拍板 | 是否有 Evidence-first 风险 | 可见收益 |
| --- | --- | --- | --- |
| 阶段 1 P1-1 | 否 | 无 | 研究库跨会话、不再静默丢数据 |
| 阶段 2 P2-3 | 否 | 无（消除假进度，更诚实） | 等待页显示真实阶段 |
| 阶段 3 P2-2 | 需选路线，默认已给定 | 低（有防护要求，见§5.3） | 研究可带走成文档 |
| 阶段 4 P1-2 | **是** | **有（核心）** | 数据刷新不用重跑模型 |

**关键判断**：阶段 4（P1-2 证据快刷）在原清单里排在 P1，但它实际上是四项里**最贵、且唯一触碰产品底线**的一项。按清单字面执行会一上来撞最硬的墙。放在最后，前面三项的经验（尤其是 indexdb 适配与打印视图的数据结构梳理）也会让它更好做。

## 3. 阶段 1 — P1-1 研究历史持久化（IndexedDB）

### 现状（已核验）

- 持久化**已经存在**，在 localStorage：`shelf.ts:55-59`（saved / recent / library）、`:168`（`stocklens.research.${code}` 存整份 payload）。读取是 `sessionStorage ?? localStorage` 双读（`:142`、`184`）。
- 真正的问题有两个，都不是"没有持久化"：
  1. **内存态丢失**：`payloadCacheRef` 有 30 分钟 TTL，整页刷新后必然重走完整 init。
  2. **静默配额失败**：`writeList`（`:151-157`）与 `saveResearch`（`:168`）都用裸露 `try/catch` 吞掉异常，包括 `QuotaExceededError`。多存几家公司的全量日线后会**无声地停止入库**，界面完全看不出来。
- `tests/shelf.test.ts` 只测纯函数与"无存储环境下退化为不抛错"，改 storage 层不影响这 8 个用例。

### 做什么

1. 新增 `src/lib/v5/idb.ts`：极小封装（项目无 `idb` / `dexie` 依赖，见 package.json；加依赖 vs 手写约 100 行，倾向**手写以避免新增依赖**）。要求：失败必须降级到 localStorage 而不是静默丢弃；`QuotaExceededError` 必须**上报**给调用方，由 UI 决定如何提示。
2. 改造 `shelf.ts`：`loadSaved/saveSaved/loadRecent/saveRecent/loadLibrary/saveLibrary/saveResearch/loadResearch/saveCanvas` 改为异步；保留现有 key 名称做一次性迁移，不丢用户已有数据。
3. 适配调用方：`ResearchCanvas.tsx`（约 8 处）、`ResearchHome.tsx`（约 6 处）。重点处理 async 化后的首帧竞态（该组件存在 400 行级 useEffect）。
4. UI：研究库标注「仅保存在本机」，且**存储失败时要如实告知**（不能因为"这是容错"就藏起来）。
5. 保留 30 分钟 TTL 的语义，但把"refresh 后要不要复用 IndexedDB 里的 payload"作为显式决策写进代码注释。

### 不做

- 不做账号、不做跨设备同步。
- 不为了"跨会话"而把 payload 存成新结构（沿用现有 payload 形状，只是换存储后端）。

### 验收

- `vitest run` 全过（含新增的 shelf 异步用例，且原 8 个用例不删不改语义）。
- 真实浏览器实测：**写入数据 → 完全关闭标签页 → 重开 → 研究库内容仍在**；对照组：在隐私模式下不报错、退化为空。
- 构造配额超限场景（写入大 payload 直至失败），确认 UI **有可见提示**，不是无声失败。

### 风险

- async 化引入首帧竞态 → 缓解：改动用最小 diff，跑全量测试 + 浏览器实测双保险。
- 迁移逻辑写错会丢用户现有数据 → 缓解：迁移前先读旧 key，写新库成功后再决定是否清理旧 key，**不做就地删除**。

## 4. 阶段 2 — P2-3 init 改为真实分阶段进度

### 现状（已核验）

- **当前进度是假的**：`InitialResearchLoading.tsx:31` → `elapsedSec < 4 ? 0 : elapsedSec < 10 ? 1 : 2`，纯按秒表切段，与系统实际在做什么无关。
- 现有三个步骤（`STEPS`，`:7`）恰好对应真实阶段边界：
  1. 「连接公司与行情数据」→ `loadTruth`（实测 0.17–0.6 秒）
  2. 「校验研究证据」→ `buildContextFromTruth` + 证据打包
  3. 「组织研究角度」→ framer + composer（两次模型调用，占 94–97% 耗时）
- init 调用点两处：`ResearchCanvas.tsx:411` 与 `:1618`。

### 做什么

1. `init-space.ts`：给 `initResearchSpace` 增加可选 `onPhase` 回调（**不改变现有函数签名与返回值**，`tests/research-init.test.ts` 有 5 处直调，保持不变）。
2. `api/research/init/route.ts`：改为分块返回（Route Handler 下用 `ReadableStream` + NDJSON）。保留现有 AbortController / 请求序号竞态防护。
3. `ResearchCanvas.tsx` 两处 fetch：改为按行读取并驱动 `InitialResearchLoading`。
4. 阶段文案沿用现 `STEPS`，但要保证：**没到那个阶段就不显示完成**。

### 不做

- 不做假百分比、不做剩余时间预测（README 明确_product choice_）。
- 阶段失败时不做"看起来还在进行"的修饰。

### 验收

- `tsc` / `eslint` / `vitest` 全过。
- 真实浏览器实测：抓取 NDJSON 各帧时间戳，确认三个步骤的 `active/complete` 切换**由服务端事件驱动**，而不是 4 秒 / 10 秒。对照组：断网或强制失败时，界面明确显示失败而非停在半完成状态。
- **明确验证生产环境**：本地能流式不等于线上能流式，CDN / 反向代理可能缓冲分块 read。这一项必须在部署目标上验证，不能只在 localhost 断言。（此项是阶段 2 最大的未知成本。）
  - **状态（2026-10-08 17:00）：✅ 已验证通过**。生产实测（`curl -N` 经代理，6 秒抓帧窗口）：`step0 active`（连接后毫秒级到达）→ 2.4s `step0 complete` → 0.8s `step1 active` → 0.8s `step1 complete` → `step2 active`（模型调用中，窗口截止属预期）。各帧在不同时间点逐帧到达，证明 Vercel 边缘**未缓冲** NDJSON 响应；若被缓冲则 6 秒窗口内应一帧都收不到（帧会堆积到响应结束才倾倒）。生产 loadTruth 耗时约 2.4s（本地 0.17–0.6s），差异来自冷启动与网络往返，属正常。回退方案（轮询式阶段接口）无需启用。

### 风险

- `Server-Timing` 调试头与流式响应冲突（现有 `route.ts` 有延迟审计头）→ 需决定保留哪个，倾向保留流式、调试头改在开发分支。
- 生产代理缓冲 → 若实测被缓冲，**回退方案是轮询式阶段接口**，整体降级但仍比假进度诚实。这个不确定性要在阶段 2 结束时如实汇报。

## 5. 阶段 3 — P2-2 研究笔记导出（打印版）

### 现状（已核验）

- 需要的数据**在前端已完整可得**：claims（`GroundedStatement`，含 `evidenceIds`）、evidence 的 `statement` / `freshness` / `verifyStatus`、metrics 的 `value` / `unit` / `period` / `calculationMethod` / `sourceFields`。
- 项目**没有任何** `@media print`、`window.print()`、PDF 依赖或 SSR 打印路径（全库检索为空）。
- 注意：v5 画布自身对 `sourceFields` 的渲染数为 0，目前只有 `ReadingV3.tsx` 渲染来源与 freshness——导出视图不能依赖画布 DOM，必须直接从数据渲染。

### 路线（默认走 (a)，需确认）

- **(a) 打印视图 + `@media print` + `window.print()`** ← 推荐。0.5–1 天，**零新增依赖**，产物由浏览器打印对话框生成 PDF。
- (b) 真·PDF 文件导出：2–4 天，需新增依赖，且 `jsPDF` 要嵌入 CJK 字体（体积与授权问题）。

### 做什么（路线 a）

1. 新增导出视图：从 payload 数据渲染「结论 + 证据 + 来源」，不复用画布 DOM。
2. `@media print` 样式：隐藏导航/控件、分页控制、页码。
3. 入口放在 Reading / 画布的合理位置，文案说清这是"打印 / 另存为 PDF"。

### 必须做到（否则与 Evidence first 冲突）

导出的文档看起来会比界面更像一份"确定性研报"，所以必须**强制带上**这些，缺一项就宁可不做：

- 每家公司/每个研究的 `dataAsOf` 与 `retrievedAt`；
- 每条证据的 freshness 与 `staleQualifier`（stale 时的限定语必须原样带出）；
- **UNKNOWN 分区必须导出**，且保留其 `unavailableReason`；
- `spaceId`、导出时间；
- 明确的「不构成投资建议」。

### 验收

- `tsc` / `eslint` / `vitest` 全过。
- 真实浏览器实测：`Ctrl/Cmd+P` 预览与实际 PDF 输出一致；确认上述 5 项必带元素**全部出现**；确认 skip stochastic 场景（含 stale 与 UNKNOWN 数据的公司）导出正确。

## 6. 阶段 4 — P1-2 证据快刷

> **本阶段开始前必须先拿到 §8 的口径决定**，否则不做。

### 现状（已核验）

- claim 是 LLM 自由文本：`src/lib/ai/types.ts:34` `GroundedStatement { text, evidenceIds }`，由 synthesizer 生成，**文本里必然引用证据数字**。
- 证据 ID 是确定性派生的：`EV_FACT_${metricId}`（`fact-builder.ts:338`），重算后 ID 不变，可原地替换。
- 现有 debug 端点不可用：`/api/debug/evidence` 被 `productionDebugRouteResponse` 拦截，且不传 `retrievedAt` / 行业 / 事件，与 init 产物**不等价**。需要新增 `/api/research/refresh`，复用 `loadTruthForResearch`。

### 核心难点（不是工程，是产品口径）

只刷数字、不重跑模型 → claim 文本所引的数字变了，但文本没变，**结论就无法再回溯到它引用的证据**。这直接违反 Evidence first。两条路：

- **路线 A（推荐）**：给受影响 claim 打上「证据已更新，该结论为更新前生成」的可见标记，并提供"重新组织该维度"的入口。诚实、成本低，但"快刷"的爽感打折。
- 路线 B：对受影响维度自动重跑 composer。体验连贯，但那就基本等于重跑，违背"快路径"的初衷且成本和两次模型调用相当。

倾向 A。**已拍板（2026-10-08，用户确认路线 A，含「重新组织该维度」入口）。**

### 做什么（以路线 A 为前提）

1. 新增 `/api/research/refresh`：复用 `loadTruthForResearch`，只重算数据层。
2. 按 `timeSensitive`（`freshness.ts`）过滤出可刷新的证据范围；metrics / evidence / marketHistory / trend 必须**同源**刷新；`retrievedAt` 一并更新，否则刷完仍判定 stale。
3. 前端合并后重跑 `evidence/validate.ts`；数字只能在服务端算。
4. 受影响 claim 打标记（路线 A 的产物）。
5. UI：只对确属 stale 的行情类证据提供入口，且刷新前后都要显示数据时间。

### 验收

- `vitest` 全过（含"刷新后 claim 标记"的新用例）。
- 真实浏览器实测：构造 stale 数据 → 触发快刷 → 确认①数字更新②`retrievedAt` 更新③受影响 claim **带可见标记**④刷新过程中失败时能明确报错并回滚到刷新前状态。
- 反例测试：非行情类（如财务报告期）证据**不提供**快刷入口。
