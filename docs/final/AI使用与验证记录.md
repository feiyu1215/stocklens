# AI 使用与验证记录 / AI Usage & Validation

本文件说明三件事：**哪些 AI 参与了什么**、**产品内部哪些环节用 AI**、以及**人在哪些地方否决或纠正了 AI**。

它要证明的不是"用了 AI 写代码"，而是：**候选人定义了 AI 该做什么、不该做什么、什么时候不能相信 AI，并把这些判断固化成了产品机制与验证机制。**

---

## 3. How AI Participates Inside StockLens

**确定性层（LLM 禁入）——Truth Layer**
扶摇数据适配 → 标准化 → **确定性指标引擎**（同比、单季还原、区间收益、年化波动、最大回撤、估值比较、行业相对表现）→ **证据引擎**（FACT / INFERENCE / UNKNOWN 的构造、冲突规则、引用完整性）。缺失即 `null`（绝不以 0 冒充），真实 0 不改写，单季与累计口径严格分离。

**AI 层——三处受约束的调用**

| 环节 | 输入 | 输出 | 约束 |
|---|---|---|---|
| **Research Framer** | 公司身份 + 行业 + 由真实指标推导的 Capability Manifest + 用户问题（**看不到任何数字**） | 4–6 个研究维度（自由命名 + 理由） | 只能命名能力清单内的方向；label 重复/引用不存在的能力/理由里出现数字都会被校验拒绝 |
| **Composer** | 某维度下**已被确定性打包**的紧凑证据（白名单字段） | claims（绑定 Evidence ID） | 引用的证据必须真实存在；伪造即整体失败并修复重试一次 |
| **Follow-up** | 当前 scope + 相关证据 ID | 有依据的追问回答 | 同上；失败只在线程内降级 |

**边界**：LLM 不能调用数据源、不能重算数字、不能新增或修改证据、不能评级或给建议。任一校验失败 → 修复一次 → 仍失败则该维度 `synthesis = null`，**证据照常返回**：AI 的失败不会污染事实层，也不会被伪装成正常结论。

### 4.2 核心案例（按对产品判断的体现程度排序）

#### 案例 1｜产品定义：从"AI 给结论"到 Evidence-first research

**问题**：早期形态天然会滑向两个方向之一——传统个股看板（把数据摆出来，结论留给用户拼），或者让 LLM 直接给出"综合判断"。

**判断**：产品不应替用户做投资决策；AI 应该组织**研究过程**。于是把产品重构为 Evidence-first：用户从研究问题出发，沿维度 → 结论 → 证据逐层深入，而不是拿到一个分数。

**最终机制**：Research Canvas → Dimension → Claim → Evidence → Follow-up Research；核心原则写进产品文案：*Evidence first. Conclusions second.* 所有输出里没有评分、没有评级、没有买卖建议。

#### 案例 2｜AI 架构：确定性与 LLM 的职责边界

**问题**：让 LLM 计算或直接推断财务指标很省事——但它不可审计，单位与口径会漂移。

**判断**：**金融计算必须确定、可审计**。区间收益、年化波动、最大回撤、同比增长、单季还原、估值比较、财务比率一律由 Metric Engine 计算；LLM 只接收 Evidence 并解释它。

**最终机制**：Truth Layer → Evidence → grounded LLM interpretation。这样做的收益是准确的数字、可追溯的来源（`sourceFields` + `calculationMethod` + 单位 + 样本数）、一致的口径与统计处理。这是 **AI 系统设计**决策，不是单纯的工程选择。

#### 案例 3｜Grounding：无证据时返回 UNKNOWN，而不是生成合理答案

**问题**：用户添加一个数据不支持的研究角度（如"库存压力"— 扶摇没有库存字段；或银行没有毛利率类指标）时，模型完全可以写出一段听起来很专业的解释。

**判断**："没有证据"是**正常的产品状态**，不得用合理的文字补全无法验证的结论。

**最终机制**：该维度落为 `UNKNOWN`，携带 `unavailableReason` 与缺失数据项（能力清单里没有的指标），UI 以独立分区呈现并明确写"这不是负面证据，也不是系统错误"。实测「库存与周转压力」正确返回 UNKNOWN + 证据不完整。

#### 案例 4｜产品定义：固定维度 → 动态 Research Framer

**问题**：固定一套诊断维度实现最简单，但不满足"AI Native"的要求——银行和制造业的研究结构本来就不该一样。

**判断**：研究维度必须由**公司类型 + 用户问题 + 真实数据能力**共同决定，模型可以自由命名维度，但只能在能力清单范围内。

**最终机制**：Research Framer（温度 0）+ Capability Manifest（由真实可得指标推导）。实测差异：制造业（美的）得到「盈利质量 / 增长韧性 / 现金转化能力 / 估值相对位置 / 市场与行业相对表现 / 股东回报与公司行为」；银行（招商）得到「盈利质量与资本回报 / 资产质量与风险抵补 / 估值安全边际与行业相对 / 市场相对表现与波动 / 股东回报与分红可持续性」。

#### 案例 5｜AI 架构：Evidence Context Budget

**问题**：早期做法倾向于把全部证据塞进合成调用。

**判断**：更多上下文不等于更好——它带来噪声、延迟、注意力稀释，以及更难控制的合成结果。

**最终机制**：确定性打包（冲突 > 推断 > 未知 > 负面 > 正面；主维度加权且每维度至少 1 条；单维度上限 4；inference 的 `basedOn` 依赖闭包必须带上；按研究意图设总量上限，当前实现为 SOFT_MAX 14 / HARD_MAX 18，多数意图 10–12）。**全量证据仍然保留给用户钻取**——被裁掉的不是事实，只是进入模型的那一份。

#### 案例 6｜金融语义：排名方向与低基数放大

**问题（两个真实案例）**：
1. 热榜排名数值从 323 变为 334，AI 初版叙述写成"关注度提升"——但热榜**数字越小越靠前**，数值变大意味着排名后移；
2. 某期经营现金流同比 −1600.72%，AI 初版写成"现金流极端恶化"——真实原因是上年同期基数极低（绝对值约 2.48 亿），数学正确但语义误导。

**判断**：**数学正确 ≠ 决策可用**。方向必须由确定性规则判定，极端百分比必须带解释而不是照搬数字。

**最终机制**：
- 排名方向在 `src/lib/data/events.ts` 中由 `earliest.rank - latest.rank` 判定并生成模板化陈述（代码注释即写明"数字越小排名越靠前"），**模型不得改写措辞**；
- `src/lib/metrics/interpretation.ts` 提供 scale-aware 护栏：上年同期绝对值 < 历史单季中位数 ×10% 且样本 ≥4 → `low_base`；正负号切换 → `sign_flip_base`；|同比| ≥ 500% → `extreme_change`。护栏**只产出解释元数据，绝不修改数值**。
- 真实 −1600.72% 场景已被测试锁定（`tests/event-risk.test.ts`，标注"真实 -1600% 场景"）。

#### 案例 7｜合规与数据时效：报告期 ≠ 过期

**问题**：题目的统一规则要求"数据缺失、冲突、过期或调用失败时不得静默生成正常结论"。把"过期"理解成"数据日期不是今天"会得出荒谬结论——一份 2026-Q2 的季报永远不是"今天"，但它并没有过期。

**判断**：必须区分两类时间语义。**财务报告期**以报告期为准，不按自然日判定；**行情/估值/事件核查**是时间敏感数据，会真的过期。

**最终机制**：`src/lib/metrics/freshness.ts` 给出确定性判定——时间敏感证据按数据日期与 7 个自然日阈值判 `fresh / stale / unknown`（取不到日期一律 `unknown`，**绝不静默 fresh**）；`stale` 时结论 statement 末尾**强制**追加「该数据截至 X…当前状态无法由该数据确认」，并且 `freshness / dataAsOf / freshnessReason` 随紧凑证据进入 AI 上下文，prompt 明令不得据此陈述"当前/目前/最新"状态；证据栏展示「数据截至 YYYY-MM-DD · FRESH/STALE」。四项聚焦测试覆盖：新鲜行情、过期行情（含阈值边界）、无法判定、报告期不被误判为过期。

#### 案例 8｜系统状态：把 15–30 秒延迟做成真实的产品状态

**问题**：未缓存公司初始化需要约 15–30 秒。性能审计显示确定性数据层只占 0.17–0.6 秒，**94–97% 的时间是两次模型调用**。AI 初版的做法是在角落放一个小 loading 卡片——读起来像卡死。

**判断**：拒绝假百分比、拒绝"正在分析财务 / 正在对比同行"这类不存在的阶段描述、拒绝只放一个 spinner 让旧画布看起来冻结。**等待本身应该是一个可读、可取消、信息真实的页面状态。**

**最终机制**：全屏研究过渡——大字号目标公司身份、**真实已等待秒数**、中性占位（只表达"研究角度尚未解析"，不预写任何金融语义）、随时可用的「← 返回上一家公司」；取消后画布上明确显示「已取消等待」。缓存会话则完全走本地恢复（实测 15.8 ms、零新增请求）。同时明确**本轮不做流式/并行优化**——先测再优化，不投机改架构。

### 4.3 支撑案例：验证体系本身

以下三项体现的是**验证方法的设计**，属于工程与迭代质量，不与上面的产品定义 / AI 架构 / 金融语义同权重。

- **请求所有权与竞态**：真实浏览器网络审计发现，一次公司选择可能触发 **2 次 `POST /api/research/init`**。候选人没有当作无害重复，要求明确请求所有权、在途去重与过期响应保护。修复后：一次切换恰好 1 次 init，缓存恢复 0 次，且此后的每一轮验收都复验该计数。
- **代码 PASS ≠ 用户 PASS**：多个控件"在源码里存在、单元测试通过"，但真实用户点不到。候选人否决了"handler 存在即交互可用"的判定标准，要求以**可信的真实指针事件**、命中测试、console 与网络审计、状态恢复作为验收依据。该标准随后暴露出 7 处同类缺陷：过渡层返回按钮被同级内容层完全盖住（在按钮矩形内取 50 个采样点，0 个命中）、Demo 结束帧 CTA 位于 `pointer-events-none` 层内、首次访问提示卡盖住公司切换器列表 92% 宽度、建议研究角度因 `setPointerCapture` 把 click 改派给父元素而无法打开、说明层向下展开把自己的按钮推出视口、Reading 自带 Escape 处理器抢在全局链之前等。**单元测试对这些全都无感。**
- **Guided Demo 的调度与文案**：首版演示永远停在第 1 幕，根因是场景调度 effect 的依赖随无关重渲染变化、cleanup 反复清掉本场景定时器（修法：排程函数入 ref，effect 只依赖场景号）。功能修复后候选人继续收紧节奏与语义：文案 `60s 演示` → `快速演示`（演示实际约 30 秒，不承诺精确秒数）、`Skip` → `下一步 →`（它本来就只是前进一幕）、控制统一为「暂停 / 继续 / 退出」，并在研究空间未就绪时禁用入口。

## 5. Validation Method

四层验证，全部以可复现的证据为准，不采信"看起来对"：

**Layer 1 — 数据与指标正确性**
方法：单测 + 与上游字段对账。代表案例：字段为 `null` → `unavailable`（不是 0）；单季还原 = 本期累计 − 上季累计（Q1 取自身）；区间收益用 N+1 个收盘价；同一输入两次运行结果完全一致；真实 −1600% 场景的护栏标记。产物：`tests/metrics/*`、`tests/evidence/*`、`tests/event-risk.test.ts`。

**Layer 2 — LLM grounding**
方法：校验层 + 单测。代表案例：伪造 Evidence ID 必须失败且不被静默删除；`unknown` 必须 `confidence=low` + `unverified` + 带 `unavailableReason`；inference 的 `basedOn` 必须能解析；证据不足时必须返回 UNKNOWN。产物：`tests/ai/diagnosis-validation.test.ts`、`tests/ai/followup.test.ts`、`tests/evidence/engine.test.ts`。

**Layer 3 — 系统状态与失败行为**
方法：失败注入（`?testFailure=research-init|dimension|followup`，仅非生产构建存在，已用生产包扫描确认）+ 浏览器验收。代表案例：三类失败各自呈现失败态并可用 Retry / Back 恢复；取消切换后现场逐项还原且 30 秒内的迟到响应不会覆盖；缓存恢复零新增 init；重复请求修复后复验。产物：`docs/final/测试说明.md` 第 4 节、`docs/design-audit/task16-2/`。

**Layer 4 — 真实用户交互**
方法：真实指针（`isTrusted: true` 的浏览器输入事件，非 `dispatchEvent`）+ 真实键盘 + 命中测试 + 多视口 + console / 网络审计 + 状态恢复比对。代表案例：48 行交互清单（PASS 47 · FAIL 0 · NOT TESTED 0 · N/A 1）；本地空间操作产生 0 业务请求；一次未缓存切换恰好 1 次 init；console 0 uncaught / 0 React / 0 hydration。产物：`docs/design-audit/task16-2/INTERACTION_MANIFEST.md`、`docs/final/测试说明.md`。

## 6. Lessons / Boundaries

- **AI 最危险的地方不是算错，而是"在缺证据时仍然写得很像真的"**——所以产品的第一原则不是让模型更聪明，而是把不确定性做成显式状态。
- **把 AI 的产出当作待验证的提案，而不是结论**：每条 claims 都必须能回到具体证据 ID；任何校验失败都宁可让该维度降级，也不放行一段没有依据的文字。
- **数字的正确性由代码保证，数字的可读性由护栏保证**：低基数、符号翻转、极端百分比、排名方向这类"数学对但会误导"的情形，需要专门的解释约束。
- **不要用假状态填补等待**：不知道剩余时间就不要显示百分比，不知道系统在做什么就不要编造阶段名。
- **验证标准比验证次数更重要**：把"能点、能恢复、请求数正确、console 干净"写成硬标准，比多跑几遍更能发现问题。
- **文档只写可核验的事实**：本文件中所有数字（402 个测试 / 29 个文件、7 天阈值、14/18 条上下文预算、−1600.72% 等）都来自仓库、测试输出或浏览器审计；无法核实的量化说法一律不写。
